# Проверки и аппаратные результаты

[К оглавлению](../README.md)

## 1. Как читать статус

- **Реализовано** — поведение присутствует в текущем коде.
- **Программно проверено** — сценарий выполнен тестом, часто с подменой USB.
- **Аппаратно проверено** — обмен выполнен с конкретным подключённым T48 и чипом.
- **Экспериментально** — результат наблюдался, но режим имеет существенные ограничения.
- **Не проверено** — нет подтверждающего результата; наличие кода не заменяет проверку.

Аппаратные результаты относятся к конкретной конфигурации. Отчёты разных чипов нельзя объединять в доказательство универсальной совместимости.

## 2. Существующие smoke-тесты

Запускайте из `emmc_continue`, каждый отдельным процессом. Это важно из-за глобальных настроек protocol.py и состояния Kivy.

```powershell
..\venv\Scripts\python.exe -X utf8 smoke_layers.py
..\venv\Scripts\python.exe -X utf8 smoke_stop.py
..\venv\Scripts\python.exe -X utf8 smoke_autoconfig.py
..\venv\Scripts\python.exe -X utf8 smoke_extcsd.py
..\venv\Scripts\python.exe -X utf8 smoke_verification.py
```

Тесты используют mocks/fixtures для операций и не предназначены для реальной записи в чип. Некоторые открывают окно Kivy и требуют графическую среду Windows. Не путайте их с исследовательскими probe-скриптами, которые могут обращаться к реальному T48.

| Тест | Что проверяет | Последний сохранённый результат |
|---|---|---|
| smoke_layers.py | GPT fixture, регистры/отчёт, scatter, сборщики протокола | PASS при подготовке документации |
| smoke_stop.py | Pending USB, освобождение, следующая задача, завершение объявленного потока, отложенный abort | PASS при подготовке документации |
| smoke_autoconfig.py | Ранжирование/откат, сравнение данных и identity, VCCQ, STOP, GUI | Логика PASS; GUI assertion FAIL |
| smoke_extcsd.py | Снимки/файлы, поля, план, OTP, полная запись и readback | FAIL на проверке цвета до более поздних сценариев |
| smoke_verification.py | Сравнение, короткие чтения, ошибки, STOP, erase, пропуски, перезапуск/CID, флаги GUI | PASS после исправления restart; в ходе документации не повторялся |

`smoke_verification.py` в конце сам запускает `smoke_layers.py`. Повторный отдельный PASS слоёв не даёт дополнительного покрытия аппаратной записи.

## 3. Известные падения тестов

### smoke_autoconfig.py

В строке 79 проверяется возврат ручной частоты стандартного пресета к переменной `standard`, которая теперь сохраняется при начальном пресете «Авто» и содержит строку «Авто». После переключения на ручной стандартный пресет выбирается ручная частота. Программная часть до GUI прошла; текущий тест останавливается на этом устаревшем ожидании.

Это не основание объявлять весь тест прошедшим. Для исправления нужно отдельно задавать/запоминать ручную настройку перед проверкой независимости пресетов.

### smoke_extcsd.py

В строке 117 ожидается фиксированный цвет `(1, 0.6, 0.25, 1)`, оставшийся от прежней палитры. Текущая тема использует другую палитру. Тест останавливается на сравнении цвета, поэтому дальнейшие сценарии этого запуска не выполнялись.

В рамках документации исходники тестов и приложения не изменялись. Обновление ожиданий и полный повтор двух тестов остаются отдельной задачей.

## 4. Аппаратные подтверждения

### STOP при THGA на 8 и 30 МГц

Лог: [hardware_stop_8_30_20261030_151523.log](../hardware_stop_8_30_20261030_151523.log).

Проверены два положения STOP внутри потока на каждой частоте: порции 3 и 31. В каждом случае завершались все 64 порции текущего 1-МиБ потока, следующий поток не начинался; затем прошли повторное открытие, чтение и новая запись с readback без переподключения T48.

| Режим | Измеренное завершение после STOP |
|---|---|
| THGA 8 МГц | Около 1.77 и 1.66 с |
| THGA Legacy 30 МГц | Около 1.58 и 1.55 с |

Это измеренные случаи, не максимальный гарантированный срок. В старом логе видны предупреждения power-off, которые в текущем завершающем `close` скрыты.

### Автоподбор

В рабочем сеансе прошёл эталон на 8 МГц; оба кандидата High-Speed 30 МГц отклонены по CSD/регистрам; выбран THGA Legacy 30 МГц. Проверка состояла из регистров и повторных выборок начала/середины/конца User Area. Этот результат не подтверждает полную запись всей ёмкости.

Пример пользовательского отчёта другого установленного чипа: Foresee, MID D6, PNM C09E00, BOOT по 4096 КиБ, User Area около 59694 МиБ. Эти параметры не являются константами приложения и не должны подставляться в расчёт другого чипа.

### Исправление restart перед верификацией

До исправления повторялась ошибка WinError 121 сразу после «Верификация: перезапуск eMMC...» при записи BOOT1. Добавлено восстановление только для тайм-аута чтения ответа power-off: закрытие/открытие USB, init, CID, затем обычный readback.

В аппаратной проверке THGA Legacy 30 МГц:

- прочитаны все 4194304 байта BOOT1;
- тайм-аут power-off воспроизвёлся;
- USB переоткрылся, init/CID прошли;
- BOOT1 прочитан снова, все байты совпали.

В этой проверке запись/стирание не выполнялись. Полный повтор сценария BOOT1 → BOOT2 → Userdata после исправления не подтверждён. Результат этого опыта сохранён в истории выполнения, отдельного лог-файла для него не заявлено.

### Короткие чтения 30 МГц

[probe_30_legacy_read_results.json](../probe_30_legacy_read_results.json) и [исследование](../clock_investigation.md) описывают 5 успешных запусков с сравнением 1 МиБ против 8 МГц на соответствующем чипе. Частота и ширина шины прибором не измерялись. Короткий тест не доказывает устойчивость всей ёмкости.

## 5. Неуспешная длинная запись

Логи:

- [hardware_optimized_20261030_142147.log](../hardware_optimized_20261030_142147.log): 30 МГц, сбой инициализации, данные не отправлены.
- [hardware_checked_usb_20261030_143257.log](../hardware_checked_usb_20261030_143257.log): T48 недоступен/занят, запись не началась.
- [hardware_optimized_8mhz_20261030_142817.log](../hardware_optimized_8mhz_20261030_142817.log): анализ 3 ГиБ, стирание User Area, контроль первых 32 МиБ; прежний длинный поток завершился тайм-аутом.

Последний опыт относится к реализации до ограничения завершённых потоков до 1 МиБ. Счётчик отправленных байтов в диагностике не доказывает их программирование в eMMC. Образ имел FF-область, а чип стирался в 00, поэтому карта не давала пропусков. **Полной успешной аппаратной верификации 3 ГиБ нет.**

## 6. Что ещё не подтверждено

- Универсальная совместимость пресетов с любым производителем/адаптером.
- Длительная полная запись/чтение всей ёмкости после всех последних изменений.
- Физические CLK, ширина шины и напряжения измерительным прибором.
- Работа RST_n как физического вывода после изменения регистра.
- Полноценное восстановление Android Sparse со всеми типами чанков.
- Ручное стирание с гарантированной проверкой всей области.
- Работа NAND, SPI, GPP, authenticated RPMB read/write.
- Чистая установка/сборка на другой машине и все версии Windows.

## 7. Минимальный план проверки будущих изменений

Для изменений протокола/сессии — существующие тесты слоёв, STOP и затронутых операций. Для верификации/оптимизации — smoke_verification с контролем коротких данных и несовпадений. Для интерфейса — соответствующие GUI assertions с актуальной палитрой и начальным пресетом.

Аппаратные проверки начинайте с идентификации и чтения. Перед записью фиксируйте CID, ёмкость, область, исходный образ, параметры и разрешение на изменение данных. Read-only проверка не заменяет разрешение стирать чип с пользовательскими данными.

Для аппаратного отчёта полезны: дата, конфигурация приложения/сборки, CID, VCCQ/шина/пресет/частота, LBA и длина, хеш исходных и прочитанных данных, результат каждой фазы, STOP и последующее восстановление доступа. Хеш без правильного диапазона и размера недостаточен.
