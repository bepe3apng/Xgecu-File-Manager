# Операции, геометрия и форматы

[К оглавлению](../README.md)

## 1. Адреса и ёмкости

| Параметр | Значение / источник |
|---|---|
| Логический сектор | 512 байт |
| Порция данных T48 | 16384 байта, 32 сектора |
| Завершённый поток записи | До 64 порций, то есть 1 МиБ |
| Порция команды стирания | До 131072 секторов, 64 МиБ |
| User Area | `little_endian(EXT_CSD[212:216]) × 512` байт |
| Каждая BOOT | `EXT_CSD[226] × 128 × 1024` байт |
| RPMB в отчёте | `EXT_CSD[168] × 128` КиБ |

Для включительного диапазона `[first, last]` размер равен `(last - first + 1) × 512`. Байтовый адрес начала — `first × 512`. МиБ = 1048576 байт, ГиБ = 1073741824 байт. Некоторые старые подписи GUI/отчёта говорят MB/KB, хотя расчёты используют степени 1024.

Адрес LBA интерпретируется внутри выбранной аппаратной области. BOOT1 LBA 0 и User Area LBA 0 — разные места. GPT/MBR относится к User Area. Редактор и операции общего назначения для GPP/RPMB не реализованы.

## 2. Чтение

`_dump_stream` объявляет число порций, принимает данные последовательно и записывает в файл только нужное количество байтов последней порции. Несовпадение длины USB-порции или итогового размера файла считается ошибкой. В памяти находятся текущие блоки, а не весь дамп.

`read_sectors` для небольших запросов выравнивает начало вниз к 32 секторам, читает достаточное число порций, затем вырезает запрошенный диапазон. Это используется при автоподборе, контроле стирания и анализе разметки.

Частичный файл после прерывания не удаляется автоматически и не является завершённым резервным образом. Возобновление дампа с места остановки не реализовано.

## 3. RAW и дополнение последней порции

Полная запись BOOT1/BOOT2/USER рассматривает любой файл как RAW. Файл `.img` по расширению не становится автоматически Sparse. Для RAW карта содержит один сегмент `(relative_lba=0, file_offset=0, length=file_size)`.

Размер передачи округляется вверх до 16 КиБ. Функция `_fill_chunk` дополняет последнюю неполную порцию нулевыми байтами 00, независимо от ERASED_MEM_CONT. Поэтому неполный хвост FF-образа после дополнения не считается целиком заполненным FF и передаётся. Верификация сравнивает исходную длину файла, а не дополнительные байты выравнивания. Для сохранения данных за концом записи используйте заранее подготовленные образы, кратные 16 КиБ, и корректные границы диапазона.

Проверка полной области запрещает выход округлённого размера за её ёмкость. Меньший образ разрешается. При включённом стирании весь остаток области стирается; при выключенном — передача последней дополненной порции всё равно затрагивает байты до конца этой порции.

## 4. Предварительное стирание и оптимизация

Последовательность для записи всей аппаратной области:

1. Проверить файл, инициализировать eMMC и определить ёмкость.
2. Определить заполнение после стирания: FF при установленном бите 0 `ERASED_MEM_CONT[181]`, иначе 00.
3. Прочитать образ с диска порциями 16 КиБ; построить объединённые участки «передать / пропустить».
4. Выбрать аппаратную область и стереть её целиком командами до 64 МиБ.
5. Проверить чтением ожидаемое заполнение.
6. Передать участки данных завершёнными потоками до 1 МиБ.
7. При включённом флаге перезапустить eMMC и сравнить весь файл чтением.

Пропускаются только целые передаваемые порции, совпадающие с ожидаемым заполнением. Для неполного конца решение учитывает дополнение порции. Последовательные одинаковые решения объединяются в карту; образ дополнительно читается до стирания, что позволяет заранее сообщить объём передачи и пропуска.

**Без предварительного стирания пропуск 00/FF для RAW не выполняется.** Нули являются полноценными данными и должны заменить прежнее содержимое.

У FF-образа на чипе с заполнением стирания 00 не будет выигрыша от пропуска FF. Совпадение сигнатуры файла с «пустотой» не определяет физическое содержимое стёртого чипа.

Файл не следует изменять между анализом и записью. Код обнаруживает ряд неполных чтений/изменений размера, но не фиксирует криптографический снимок содержимого: замена байтов без изменения размера может не быть обнаружена заранее, особенно в участках карты пропуска. Итоговая верификация необходима.

## 5. Контроль стирания

Проверяется весь выбранный диапазон, если он не больше 32 МиБ, либо первые 32 МиБ большего диапазона. Чтение идёт частями до 1 МиБ; каждый байт сравнивается с 00 или FF. Ошибка чтения, неполная длина, несовпадение или STOP запрещают переход к записи.

Стирается вся область, но чтением подтверждается только указанная выборка. Это не доказательство пустоты всего большого раздела. Проверка данных образа после записи охватывает иной диапазон — длину образа, и включает пропущенные в RAW блоки заполнения.

Для записи диапазона из таблицы со стиранием дополнительно проверяются:

- `0 <= start_lba <= end_lba < SEC_COUNT`;
- активный `ERASE_GROUP_DEF[175]` и ненулевой размер группы;
- выравнивание начала и конца+1 по `HC_ERASE_GRP_SIZE[224] × 1024` секторам;
- размещение каждого округлённого сегмента внутри выбранного раздела.

Невыровненный GPT-раздел может читаться, но его запись с предварительным стиранием будет отклонена. Отключение стирания меняет гарантии: пропуск заполнения отключается, а защита границ в этом маршруте слабее; см. ниже.

## 6. Верификация

`verification.verify_file` принимает список `(device_lba, file_offset, length)` и выполняет:

1. Проверку запроса STOP.
2. Перезапуск eMMC с прежними настройками и проверкой CID.
3. Выбор нужной аппаратной области.
4. Потоковое чтение и побайтовое сравнение с файлом.
5. Итог по всем проверенным блокам.

Для каждой несовпавшей порции выводится первое различие: область, байтовый адрес на устройстве, смещение в файле, ожидаемый и прочитанный байт. Подробности ограничены 50 сообщениями; итоговый счётчик считает порции с ошибками, а не число различающихся байтов.

Неполный USB-блок, преждевременный конец потока, пустой диапазон, неполное чтение файла, изменение CID или ошибка повторной инициализации не считаются успехом. При STOP верификация возвращает отрицательный результат. Успешное завершение записи RAW выводится только после успешной включённой верификации.

При тайм-ауте 121 именно чтения подтверждения power-off допускается переоткрытие USB. Это не универсальное игнорирование USB-ошибок: ошибки отправки команды, другие коды, невозможность открыть T48, ошибки init/CID/readback сохраняются.

Проверка не доказывает загрузку целевого устройства, сохранность после длительного хранения, корректность файловой системы или соответствие образа конкретной плате. Для меньшего RAW-файла остаток области за ним не сравнивается.

## 7. Android Sparse: частичная реализация

`ImageProcessor` распознаёт magic `0xED26FF3A` в маршруте `write_lba_range`. Текущий алгоритм:

| Тип чанка | Реальное действие |
|---|---|
| RAW `0xCAC1` | Добавляет сегмент данных из файла |
| FILL `0xCAC2` | Пропускает, не разворачивает 4-байтовый шаблон |
| DONT_CARE `0xCAC3` | Пропускает адресный диапазон |
| CRC32 `0xCAC4` | Пропускает данные, не проверяет CRC |

Это **не полноценная поддержка Android Sparse**. Ненулевой FILL не восстанавливается. Без предварительного стирания в пропущенных местах остаются прежние данные. После стирания там остаётся заполнение чипа, которое не обязано совпадать с требуемым шаблоном Sparse.

Верификация этого маршрута сравнивает переданные RAW-сегменты, включая пропуски заполнения внутри них; она не сравнивает развёрнутый логический образ в участках FILL/DONT_CARE. Поэтому сообщение об успешной верификации Sparse не подтверждает восстановление всего логического образа.

Парсер имеет ограниченные проверки заголовков, расширений и усечённых данных. Не заявлены полная проверка версии, всех размеров, суммарного числа блоков и CRC. Для надёжного восстановления предварительно преобразуйте Sparse в полный RAW внешним проверенным инструментом, затем проверьте размер и используйте подходящий маршрут записи.

## 8. Диапазоны таблицы и ограничения границ

При `erase_before=True` проверяется размещение округлённых сегментов до стирания. При `erase_before=False` текущий `write_lba_range` может пропустить сегмент, начало которого за пределами раздела, или обрезать длину до конца диапазона, затем сообщить успех по оставшимся данным. Передача всё равно округляется до 16 КиБ и для невыровненного конца может затронуть соседние байты. Это ограничение реализации, а не рекомендуемый способ обрезки образа.

Используйте образы, соответствующие размеру/разметке, проверяйте кратность и журнал; для полного аппаратного восстановления предпочтителен RAW всей User Area. Таблица разделов не предоставляет автоматической транзакционной защиты соседних разделов.

## 9. GPT, MBR и определение файловых систем

Инициализация читает первые 64 сектора User Area. По `EFI PART` в LBA 1 выбирается GPT; по `55 AA` в конце LBA 0 — MBR. GPT-парсер рассматривает до 128 записей, находящихся в полученном буфере. MBR-парсер выводит четыре первичные записи; обход цепочек EBR расширенных разделов не реализован.

Проверка CRC GPT, резервного GPT в конце диска и полная структурная валидация разметки не реализованы. Подпись MBR сама по себе не доказывает корректность всех записей.

Для определения ФС считываются первые четыре сектора раздела и проверяются сигнатуры EXT4, F2FS, EROFS, SquashFS, NTFS, exFAT, FAT32, FAT16/12, Android boot и Sparse. Это распознавание заголовка, а не монтирование, проверка целостности или работа с файлами. `(blank)`, `?` и `err` не являются исчерпывающей диагностикой содержимого.

## 10. Ручное стирание

`erase_blocks` использует команды до 64 МиБ и ожидание готовности. В отличие от `_erase_before_write`, этот маршрут не проверяет чтением результат и при ложном результате `erase_wait_ready()` только пишет предупреждение, продолжая цикл. Конечный общий успех не отменяет предыдущую ошибку.

GUI допускает резервные значения при некорректном вводе LBA; низкоуровневая функция не имеет того же полного набора проверок диапазона, что предварительное стирание записи. Перед ручным стиранием вводите точные десятичные адреса, проверяйте расчёт размера и аппаратную область. Secure erase, sanitize и гарантированное физическое уничтожение данных не реализованы.
